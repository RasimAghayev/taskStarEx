# Contributing

Thanks for your interest in `taskStarEx`. This document describes how
bugs/features are reported, how a pull request should be shaped, and how
it gets reviewed and merged.

## Code of Conduct

Participation in this project is governed by
[`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md) (Contributor Covenant 2.1).

## Reporting bugs / requesting features

- **Security vulnerability?** Do not open a public issue — see
  [`SECURITY.md`](SECURITY.md) for private reporting.
- Otherwise, open an issue using the matching template:
  - [`.github/ISSUE_TEMPLATE/bug.md`](.github/ISSUE_TEMPLATE/bug.md)
  - [`.github/ISSUE_TEMPLATE/feature.md`](.github/ISSUE_TEMPLATE/feature.md)
  - [`.github/ISSUE_TEMPLATE/docs.md`](.github/ISSUE_TEMPLATE/docs.md)
- Never paste a real secret, token, or credential into an issue, even
  redacted-looking. If one slips in, it is treated as compromised the
  moment it's posted — rotate it, don't just edit the issue.

## Development setup

Everything is Docker-first (nothing on the host is treated as
verification):

```bash
make env       # .env scaffolding
make verify    # test stage (both apps) + build — must be green before any PR
make up        # start the stack (depends on make verify)
make shell      # backend dev shell (composer/phpunit/pint available)
make shell-fe   # frontend dev shell
```

See [`README.md`](README.md#getting-started-docker-first) and
[`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md) for the full command list and
environment variables.

**Code is written only inside `projects/worktrees/taskStarEx/`** if you
are working within the larger `RasimAghayev` multi-repo governance
program this repo is part of (see that program's own `CLAUDE.md`/
`PROMPT.md` if you have access to it) — `projects/repos/taskStarEx` is
the clean canonical clone and is never edited directly. If you're a
regular outside contributor working on a normal clone of this repo,
this distinction doesn't apply to you; just follow the branch/PR rules
below.

## Branching

- This repo uses a **3-branch model**: `preview` (integration) →
  `test` (stabilized) → `main` (production-ready, the default branch).
  **Every PR targets `preview`** — never `test` or `main` directly.
- Branch names: `phase-<n>/<topic>` for this program's own phased work,
  or a descriptive `<type>/<short-topic>` (e.g. `fix/csv-import-header`)
  for an ordinary contribution — cut from `preview`.
- Never push directly to `preview`, `test`, or `main`. All three are
  branch-protected (required PR, required green status checks, no force
  push, administrator bypass disabled).

## Commits

[Conventional Commits](https://www.conventionalcommits.org/):
`feat`, `fix`, `refactor`, `perf`, `test`, `build`, `ci`, `docs`,
`chore`, `revert` — with `!` or a `BREAKING CHANGE:` footer when
applicable. **One logical change per commit.** Don't squash unrelated
changes (a dependency bump, a bug fix, and a doc update) into one
commit.

## Pull requests

1. `make verify` must be green locally before you open the PR — include
   the command and its exit code in the PR description (see the PR
   template).
2. PR title is itself a Conventional Commit title.
3. Fill out
   [`.github/PULL_REQUEST_TEMPLATE.md`](.github/PULL_REQUEST_TEMPLATE.md)
   in full — including the AI-attribution checkbox below.
4. **Never `--no-verify`** — if a pre-commit/CI hook fails, fix the
   underlying issue; don't bypass it.
5. A maintainer reviews and merges once CI (`.github/workflows/ci.yml`)
   is green on the PR. One PR per logical unit of work (this program's
   convention is also one PR per phase per repo, where applicable).

## AI-attribution rule

**No commit, PR title, PR description, or PR/issue comment on this
repository ever carries an AI co-author or session trailer** (e.g.
`Co-Authored-By: Claude ...`, a `Claude-Session:` line, or any
equivalent "generated by/with AI" marker) — regardless of what tool was
used to help write the change. Authorship is the human contributor's
alone. If your tooling auto-appends such a trailer, strip it before you
push (amend locally — never let one reach this repo, public or
private). The PR template's checklist includes confirming this.

## Review process

- Required status checks (`.github/workflows/ci.yml`'s jobs) must pass.
- `CODEOWNERS` lists the default reviewer for all paths.
- Maintainers merge via rebase-merge or a merge commit so history stays
  meaningful; squash is used only when the PR is genuinely one logical
  change.
