## Standing-decision-1 written blockers (formal record)

Per CLAUDE.md standing decision 1, an exception to "latest stable, always" requires a written blocker here, with the highest compatible version used meanwhile:

Originally **held at `^4.6.4` / npm's `v4-latest` dist-tag (`4.6.5`)** pending a Vuex→Pinia migration being separately scoped and approved. Evidence of the hold: 3 reverted Renovate cycles (PRs #56-#65) + a 4th attempt (`#67`), npm registry peer-dependency data for `vue-router@5.5.1`. The repo owner merged `#67` directly to `master` on 2026-11-17 (before this Phase 4 pass started), and on 2026-11-18 explicitly confirmed (relayed via the Orchestrator) that this was a deliberate, informed decision, not an accident — the hold is lifted, v5 is the intentional direction, and Renovate's `#69` (propose reverting to `v4.6.5`) was closed on that basis rather than merged. This is no longer a standing-decision-1 exception: adopting latest stable is now the accepted plan, not a deferred one. Two real action items remain, tracked under P1-2 (owner: Phase 6/8), not here: regenerating the `src/fe` lockfile against `pinia`+`vue-router@^5.0.0` (Phase 6 step 0 — still outstanding, the lock was never actually regenerated for this bump), and executing the Vuex→Pinia migration for real (Phase 6/8 scope, not blocker-avoidance).
2. **`picomatch` (transitive, via `vite`/`laravel-vite-plugin`/`tinyglobby`/`fdir` on `src/be`'s asset pipeline)** — `GHSA-fc5q-39xc-vjpf` ReDoS, no fix available upstream even at the newest `vite 8.3.8`/`laravel-vite-plugin 3.2.1`. **Bump to latest anyway** (nothing better exists); residual risk accepted and documented here, to be re-checked on every future `vite`/`laravel-vite-plugin` release.
